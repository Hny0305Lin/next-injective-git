# Next Injective Git 开放问题（待讨论决策）

> 项目：**Next Injective Git**（CLI：`igit` / `git-remote-inj`，合约：`repo-registry`）。架构设计见 [architecture.md](architecture.md)。
>
> MVP 不阻塞，但产品化前必须逐一定论。每项讨论后在本文件记录结论与日期。

> 实施状态同步（2026-08）：代码级安全与发布信任改动已进入合约 v0.5.0；生产部署、主网多签和 fee grant 仍以 [backlog.md](backlog.md) 的运行证据为准。

## 1. 私有仓库

**现状**：所有 packfile 公开在 IPFS，任何人可克隆。

**候选方案**：
- A. 客户端对称加密 packfile（如 age/AES-GCM），密钥经协作者公钥（链上注册）非对称分发
- B. 依赖私有 IPFS 集群 + 访问控制网关（中心化妥协）
- C. MVP 不做，先服务开源场景

**待决策**：密钥轮换（移除协作者后旧密钥仍能解历史）如何处理？

## 2. IPFS Pinning 持久化与中国大陆可用性

**现状**：仅 push 者本地 Kubo pin，节点下线数据即不可达。

**大陆可用性风险（2026-07 讨论结论，升级为 MVP 上线前必做）**：
- 公共网关（ipfs.io / dweb.link / Cloudflare）在大陆均被阻断，CLI 默认回退网关必须更换
- 官方 bootstrap 节点部分被阻断，DHT 寻址慢，冷门 CID 可能长时间不可发现
- 应对：自建 pin 节点 + 网关（香港/新加坡线路）；CLI 增加 peers 配置，启动时 swarm connect 直连自家节点绕开 DHT；网关回退默认值改为自家网关
- 同理需要验证 Injective LCD/RPC 端点在大陆的可达性并准备备选

**持久化候选方案**：
- A. 官方运营 pinning 集群（先中心化保活）
- B. 集成 Pinata / Filebase 等托管 pinning（CLI 已预留网关配置）
- C. Filecoin 存储交易（真正去中心化持久性）
- D. 代币激励的社区 pin 节点网络（长期）

**建议路径**：A → B 并行，长期演进到 C/D。因大陆可用性依赖定向连接自建节点，A 为 MVP 上线前必做。

## 3. 经济模型

- 创建仓库 / push 是否额外收费（INJ）？还是仅链上 gas？
- 存储成本（pinning）由谁承担：用户按量付费 vs 平台补贴？
- 是否发行平台代币用于存储激励与治理？发币的合规评估？

**✅ 已定案（2026-07）**：
1. **赞助流 + 仓库分成表**作为资产化第一步，下一轮合约迭代实施：`Sponsor` 消息携带资金、合约按分成表即时自动拆分转出（不沉淀资金）、`SetRevenueSplits` 仅 owner 可改、事件记录供赞助墙展示；分成份额不可转让（见第 3 条资产化边界）。**✅ 已实施（合约 v0.3.0，2026-07）**：Sponsor/SetRevenueSplits/SponsorTotals 上线，分成上限 20 人、余额归 owner、Frozen 拒收赞助；CLI `igit sponsor`/`igit splits`
2. **平台抽成 3%** 进金库（合约参数化，上限硬编码 5%）；金库首个支出场景 = 版权补贴（见 §14）。**✅ 已实施（v0.3.0）**：`platform_fee_bps` 默认 300、`MAX_PLATFORM_FEE_BPS=500` 硬编码、`SetFeeConfig` 仅 admin
3. **资产化边界（L1–L4 阶梯定案）**：
   - L1 贡献纪念 NFT：由开发者向帮助过项目的用户（issue 解答、PR 贡献）授予，无收益属性；与赞助流同轮实施
   - L2 仓库整体所有权 NFT：开发者不再维护时可链上整体转让；排期二期（E2E 跑通 + 合约审计后），一期用现成的 TransferOwnership 满足转让需求
   - L3 份额点对点转让：**禁止**——开发者只能向用户赠予 NFT，不能转让收益份额
   - L4 份额公开交易：**禁止**——收益权份额只归开发者掌握，不得变相售卖
   - 效果：平台完全退出证券风险区，无需法律意见书/牌照实体，合规负担大幅下降
- 待定：是否发平台代币（建议 MVP 不发，存储激励网络是将来发币最好理由）、pinning 成本分摊

## 4. 命名系统

**现状**：URL 使用裸地址 `inj://inj1.../repo`，可读性差。

**✅ 已定案（2026-07）：合约内置用户名注册表**
- name → 地址映射，先到先得 + 押金防抢注；注册费进金库（金库第二收入源）
- URL 升级为 `inj://alice/repo`，CLI 解析时先查用户名表再回退裸地址（兼容两种写法）
- 待细化：押金金额、用户名规则（长度/字符集/保留字）、是否允许转让/释放
- **✅ 已实施（合约 v0.5.0，2026-08）**：RegisterUsername/ReleaseUsername/ResolveUsername/AddressUsername 上线；规则：3-32 位 `[a-z0-9-]`、禁首尾连字符、禁 `inj1` 前缀；押金可配置并在释放时退还，注册费进入 treasury，保留字表由 admin 配置；CLI 会读取押金+注册费并一次性支付。主网费率和最终保留字表仍待配置。

## 5. 存储层再审视（2026-07 新增，高优先级）

### 5.1 存储后端抽象
- 现状：合约 `packfile_cids` 隐含绑定 IPFS
- 建议：改为通用 URI（`ipfs://` / `ar://` / 未来其它），为 Arweave（release 永存快照）、Filecoin（冷备）留演进空间；合约改动小、影响深远，应在主网前定案

**✅ 已定案（2026-07，技术兜底决策）**：采用通用 URI 格式（`ipfs://<cid>`）。现在改只是前缀解析，将来改需迁移全部链上存量数据；低风险高保险，字段同步更名为 `pack_uris`。**✅ 已实施（合约 v0.2.0，2026-07）**：字段已更名、合约校验 URI 格式、CLI 读写 `ipfs://` 前缀并兼容裸 CID。

### 5.2 存储粒度
- packfile 粒度（现方案）：实现简单，但跨仓库零去重（fork = 全量复制），clone 需串行下载全部历史 pack
- 对象/chunk 粒度：去重好但请求数爆炸，IPFS 上不现实
- 折中方向：定期 repack 成分层快照（全量基线 + 增量），fork 复用 CID 列表
- CID 列表增长阈值：建议 50 个或总量 500MB 触发 repack（原第 5 节内容并入）

### 5.3 内容无法删除的合规问题（硬伤，优先级高）
- IPFS 内容一旦传播无法真正删除；侵权代码、泄露密钥、违法内容的处置方案必须有

**✅ 已定案（2026-07）：三层递进屏蔽 + 平台多签委员会**
- 屏蔽分层：L1 Delisted（前端/indexer 隐藏）→ L2 Frozen（合约拒绝新 push、拒收赞助、停发 NFT、取消版权补贴资格）→ L3 链下 unpin（自家 pin 节点下架）；冻结资金流是核心惩罚——违规者不能继续用违规内容赚钱
- 执行权：平台多签委员会（建议 3/5），每次屏蔽/解除需多签，屏蔽理由文档 hash 上链，全程事件可审计（"审查行为本身透明"作为与 Web2 黑箱下架的差异化点）
- 流程：举报（链下）→ 委员会审核 → 多签执行 → 申诉（多签解除）；远期有代币后可过渡到 DAO
- 预防件：CLI push 前本地扫描常见密钥格式，发现即警告（不阻断）
- 合约实施：Repo 增加 `moderation_status` 字段（Active/Delisted/Frozen）+ 委员会地址配置。**✅ 已实施（合约 v0.5.0，2026-08）**：字段、`set_moderation_status`、独立 committee 地址、链上举报/裁决/申诉记录以及 CLI push 前密钥扫描已上线；committee 需要在主网配置为真实多签地址。

### 5.4 防滥用
- 免费 pin = 免费网盘；需要单次 push 体积上限、仓库总配额、超额按量付费（与经济模型联动）

### 5.5 其它大仓库议题（原第 5 节）
- 浅克隆（depth）：需 helper 侧按深度切 pack，复杂度高，评估需求后再排期
- Git LFS 类大文件：IPFS + 指针文件天然契合，可作差异化特性提前做

## 7. 合约治理与升级

- 合约当前 `--no-admin` 部署则不可升级；保留 admin 则有中心化升级权

**✅ 已定案（2026-07）：技术多签 admin + 14 天升级时间锁**
- 保留升级能力（migrate entry），admin 为技术多签；宣布升级后 14 天才可执行，期间社区可审查新代码、不满意的用户有充分时间迁出
- 技术多签与 §5.3 内容委员会**分设两套**：内容委员会管内容，技术多签管升级，权力分开
- 实施：testnet 阶段可先用单签 admin 快速迭代，主网部署时切换多签 + 时间锁。**✅ migrate 入口与合约内时间锁已实施（合约 v0.5.0，2026-08）**：admin 先提交精确 Wasm SHA-256 的 `schedule_upgrade`，14 天后 `migrate` 必须提交相同哈希；主网仍需把 admin 实际配置为多签并留下公告/执行交易证据。

## 8. 账号安全与所有权恢复（2026-07 新增）

- 私钥丢失 = 仓库永久失联，没有"忘记密码"；仓库带收入后被盗代价更高

**✅ 已定案（2026-07）：守护人恢复 + 转移两步制**
- **守护人机制**：日常单签不变；owner 可设守护人（如 3 选 2），守护人可发起更换 owner 地址，进入 **7 天时间锁**，期间现任 owner 可否决；覆盖密钥丢失（守护人救回）与守护人作恶（否决）两种场景
- **转移两步制**：TransferOwnership 改为发起 → 7 天等待（现任 owner 可否决）→ 新 owner 主动接受生效；防密钥被盗后秒转 + 防手滑转错地址
- 企业用户：文档引导用 Cosmos 原生多签地址当 owner（零开发成本，现在即可用）
- 合约级多 owner（地址列表 + 阈值）：不做，避免权限模型复杂化

**✅ 已实施（合约 v0.5.0，2026-08）**：TransferOwnership 改为 7 天 timelock + 新 owner 主动接受；SetGuardians/ProposeRecovery/ApproveRecovery/CancelRecovery/AcceptRecovery 已有集成测试。

## 9. Gas 与开发者体验（2026-07 新增）

- 每次 push 需持有 INJ 付 gas，对 Web2 开发者门槛极高

**✅ 已定案（2026-07）：fee grant 代付**
- 新用户前 N 次 push 由平台通过 Cosmos 原生 fee grant 代付（金库出资），降低首次体验门槛
- **✅ 策略已细化（2026-08）**：N=3 次成功 `update_ref`，总额度 0.03 INJ、7 天 TTL、30 天地址/身份冷却、每日最多 100 个 grant；要求钱包签名 nonce、唯一身份 hash、地址/身份一对一绑定和 denylist 检查。`scripts/feegrant-policy-gate.sh` 负责资格、状态、Push 计数和撤销记录；自动发放服务与真实免 gas Push 仍待部署验收。

## 11. 链下索引服务（2026-07 新增）

- 合约查询回答不了"全网仓库列表/热度排序/代码搜索"
- 二期 Web 平台必然需要监听链上事件的 indexer（隐含中心化组件，提前承认并设计开源可自部署版本）

## 12. 协作流（PR/Issue）定位（2026-07 新增）

- 纯链上（评审签名上链，贵但可信）vs 链下服务（快但中心化）vs 混合（PR 元数据上链、讨论内容 IPFS）
- 依赖关系：L1 贡献 NFT（奖励 issue/PR 贡献者）与版权选拔（issue 数量指标）均依赖本系统

**✅ 已定案（2026-07）：混合方案**
- issue/PR **元数据上链**：发起人、时间、关联 commit/ref、状态（open/closed/merged）
- **正文与讨论存 IPFS**（内容 hash 上链防篡改），展示与搜索靠 §11 indexer
- 效果：`AwardBadge` 可引用链上 issue/PR ID，贡献凭证完全可验证；版权选拔的 issue 指标有链上依据
- 产品定位随之明确：不止存储层，是**协作平台**；排期：合约 v2 之后的 v3（v2 先交付赞助/NFT/安全，L1 NFT 在 v2 阶段先允许自由文本备注奖励理由，v3 接入 issue ID）

## 13. 迁移与镜像策略（2026-07 新增，冷启动关键）

- `igit import github.com/x/y` 一键迁移
- 双向镜像模式（push 同时到 GitHub 与链上）降低试用成本

## 14. 竞品对比与差异化（2026-07 新增，影响叙事）

- Radicle（P2P 无链存储）/ Gitopia（Cosmos 专链，路线最相近）/ Protocol.Land（Arweave）
- 必须回答：为什么选 Injective 而非专链？差异化方向（借 Injective 金融基础设施做代码资产化？）

**✅ 已定案（2026-07）：差异化主方向 = 代码资产化**
- 选型背景：创始人在 AdventureX（中国最大黑客松）实地考察 Injective 后选定；看中主网稳定性、亚秒级出块，以及可借其金融基础设施做开源社区 NFT/代币
- "为什么是 Injective"的回答：继承主网安全性与亚秒级出块，更关键是现成的金融基础设施（代币发行、订单簿、链上结算）支撑仓库确权、贡献者分成、赞助流等资产化能力——这是专链（Gitopia）与纯存储（Protocol.Land）都不具备的

**✅ 新增差异化特性（2026-07）：资金池 → 优秀开源作者当地版权申请**
- 闭环逻辑：链上 commit 时间戳 = 创作过程存证（辅助证据）→ 平台资金池出资代办软件著作权等法定登记 → 链上资产（NFT/收益权）获得真实法律权利背书
- 竞争壁垒：所有竞品都停在"链上证明"，"有法律实体的代码资产"独一无二
- 张力与解法：版权登记需实名 vs 链上匿名钱包 → 设计为可选服务（自愿实名通道），形成匿名长尾/实名精品的自然分层
- 待细化 → **选拔标准已定案（2026-07）**：版权补贴资格与 **AI Agent 代码质量评估 + issue 数量 + 仓库活跃度**挂钩（不用赞助额，避免"钱说话"）；AI 评估服务与 §11 链下 indexer 共用基础设施，评估规则与结果公开；仍待细化：首期覆盖司法辖区（先中国软著）、代办服务商对接、AI 评估的具体指标与反刷分机制

- 对合约设计的约束：repo-registry 需为资产化留接口（仓库所有权已可转移，后续考虑：仓库收益地址字段、贡献者分成表、与 CW721/资产合约的组合接口）
- 风险提示（2026-07 更新）：因 L3/L4 已禁止（见 §3），证券认定风险已解除；剩余合规关注点为版权代办服务的实名/代理合规与内容合规（§5.3）；可信供应链（方向 B）能力作为资产价值的支撑适时补充，不作主叙事

## 15. 客户端分发信任（2026-07 新增）

- git-remote-inj 二进制的分发与验签（供应链攻击面）
- 最低配置：checksum 上链或 reproducible build

**✅ 已定案（2026-07）**：
- **校验和上链为必选**：每次发版将二进制 SHA-256 上链，与版本变动强绑定；用户 pull 到的产物必须能对照链上 hash 验证——项目本身靠 Web3 推动，分发信任必须同样链上化，不能例外
- **Reproducible build 为尽力目标**：能实现则最好，在项目仓库中标注构建环境与复现步骤，让开发者可自行验证
- 实施影响：合约需新增发版登记能力（版本号 → 平台产物 hash 映射），`igit` 增加自验命令（下载后比对链上 hash）

**✅ 已实施（合约 v0.5.0，2026-08）**：`RegisterRelease`/`ReleaseArtifacts` 提供不可变版本+平台 SHA-256 记录，CLI 提供 `igit release register` 与 `igit release verify`，发布目录可由 `scripts/register-release.sh` 登记。
